## Foundations & Architecture

Initial setup: Clerk for auth, Neon for hosting/DB, Drizzle as the ORM, Zod for validation. The Zod/Drizzle schema definitions turned out to be not far off from writing plain SQL tables, so that translated well early on. What didn't translate was `z.object` validation itself, or how the middleware and client-side auth actually worked under the hood — both felt opaque. Claude Code filled in those gaps from day one, which raised a real tension I wanted to name early: being comfortable with AI tools is part of the point of doing this project, but leaning on code I don't understand for a part of the stack I already find opaque (auth) is a specifically dangerous combination, not a neutral one.

Documentation got added early too — undocumented sprawl has killed past side projects, so `CLAUDE.md` was written before the codebase had much of a shape to document. Writing it also forced actually studying the schema/validation layer properly instead of treating it as a black box: schema definitions are just another way of writing SQL tables, and validation exists to guarantee that a request's shape matches what the handler expects — nothing more mysterious than that.

`CLAUDE.md` also pinned down a project-structure decision that everything downstream depends on: **all four HTTP verbs and all server actions run their own validation and route through a single service layer**, even though at the time there were no real plans to expose an HTTP API to anything. The payoff of that choice wasn't visible yet, but the reasoning was that a service layer shared between actions and routes means a future consumer (a mobile client, mainly) doesn't require re-deriving the business logic — only a new thin adapter. This is the single architectural decision the rest of the log keeps paying off.

Building the languages route on top of that pattern surfaced the first real security lesson: **server actions look like plain function calls but are exposed exactly like an HTTP endpoint** — validation has to run inside them explicitly, or they're a hole. Bare IDs needed their own UUID check (`z.uuid()`) in actions specifically, since actions don't get the same params-parsing safety net that route handlers do implicitly.

Auth itself settled on lazy provisioning: Clerk doesn't write to the app's own `users` table on its own, and the choice was to create that row lazily via `currentUser()` on first need rather than eagerly via webhooks. Simpler to implement, and not expected to cause problems as long as every code path resolves the user through the same function — a decision that held for the rest of the project.

## Phonemes

The first real feature slice: a language editor with sub-routes, navigated through a sidebar in a nested `layout.tsx`. This was also the first real exposure to how much Next.js's behavior is driven by file structure rather than explicit wiring, and the first real exposure to Tailwind — the "one class, one rule" mental model made sense quickly, but knowing what to write and not misspelling it took longer.

Phonemes got the first CRUD slice: symbol (mandatory) and IPA notation (optional) as separate fields, which doubled as the first schema change after initial setup — deliberately started with a plain column addition before anything more structurally complex. The initial subroute code came from Claude Code; the schema change itself was done by hand. Reviewing CC's output was itself instructive: the service-layer logic was fine, the frontend was ugly, and CC was noticeably less willing to rearrange existing code than I would have been left to my own devices — importing `Result<T>` from the languages module into phonemes, in particular, didn't sit right on review. First use of `drizzle-kit push` here too, confirmed against Neon directly; a plain push was the right call for a single-column addition, but looking ahead to syllable structures (a bigger structural change), migrations looked like the better tool for something that actually needs to be tracked.

Full phoneme CRUD (add/edit/delete, with symbol/weight/IPA) followed, along with heavy hand-editing of the CC-authored rows and form to make them presentable — the add and edit forms ended up looking near-identical, flagged as a future merge candidate. `Result` moved to its own file, and Svc-layer functions started getting a consistent `Svc` suffix to avoid confusion with same-named server actions. Tailwind comfort kept climbing; the remaining obstacle was CSS design sense generally, not the tool.

The add/edit forms did eventually get merged into one reusable component — which meant server-action refactoring, since editing had been built on `useTransition()` and adding on `useActionState()`. In hindsight, probably more refactor than the merge was worth. This period also included a deliberate choice to attempt the first pass at phoneme groups by hand, without AI scaffolding, specifically to verify actual understanding rather than pattern-matching against CC's style.

Phonemes also got the first HTTP API pass (list/create/delete/edit), reaching parity with the server actions, plus a middleware change so expired-session API requests return `401` instead of redirecting to Clerk's sign-in page. Because the Svc layer already carried all the logic, writing the routes was mostly "validate the input, call the same function." Testing this in Postman surfaced the session-cookie architecture: Clerk's actual session lives for 7 days, but the `__session` cookie the app checks is a 60-second JWT that `clerk.js` silently refreshes every 50 seconds in the browser. Postman doesn't do that refresh dance, so it would intermittently get HTML (the sign-in redirect) instead of JSON. Returning `401` instead of redirecting made the failure legible, and — because the architecture kept API concerns isolated from the actions the rest of the app runs on — none of this blocked the actual feature work.

## Phoneme Groups & Relations

Groups were the first feature that didn't map cleanly onto "how you'd build this in a frontend-only app." The first attempt at writing the actions by hand was inefficient and convoluted — this is exactly the use case for Drizzle's `relations()` and nested `with` queries, but there wasn't yet a working mental model for them. Querying group relationships required understanding `findMany()`'s `where` (straightforward, same as `select()`) versus its `with` (not straightforward at all). A deliberate experiment to avoid AI-generated code entirely for this section failed quickly, but it did succeed at localizing exactly which concept was missing.

Working through the actual mechanism by hand eventually produced a real explanation: querying `phoneme_groups` with `findMany()` takes a `where` matching the language ID (same as `select()`), and the `with` traverses `phonemeGroupsRelations` from the schema — `memberships: many(group_memberships)` says "go look at `groupMembershipsRelations` for how to expand this." A nested `with` inside that then does the same thing again to pull the actual phonemes. The genuine difficulty wasn't the query syntax, it was that both ends of a relationship get defined separately in the schema, so reading the connection back out requires holding both halves in your head at once.

Most of the Svc functions for `phoneme_groups` and `group_memberships` got written by hand from there. `group_memberships` is a pure join table — rows only ever get added or removed, never edited. One experiment — using `with` for IDOR validation on membership creation — turned out worse than just making a couple of separate round trips to the DB, but the bigger point stood regardless: the goal here was writing something explainable, not necessarily the most "correct" implementation for the situation.

The group-manager UI (create/delete/rename groups, assign/remove phoneme memberships) was mostly hand-written too, largely adapted from the earlier phoneme form; CC was only invoked at the end to check the result against `CLAUDE.md` conventions, deliberately treated as a self-assessment rather than a necessity. That pass surfaced no major issues beyond copy-paste leftovers and one missed convention. It did introduce a genuinely new pattern: passing every relevant ID through form components sharing the same `name` prop, with previous membership state carried via hidden inputs — not something encountered before this project, but one that recurred soon after.

The HTTP-route pass for groups (list-with-members, create, delete, list-members-by-group, add/remove members) produced the clearest architectural lesson of this stretch. Building a dedicated "get all members of a group by ID" Svc function briefly triggered regret about the earlier hidden-input approach in the actions — in hindsight, that regret was misguided: you don't want extra DB round trips just to re-fetch data the action already had in hand. More importantly, updating a group means something different to a user than it does to the API. To a user, renaming a group and changing its membership are the same action, and collapsing them is good UX. Building that same collapse into the HTTP layer would be pretending the underlying tables work like that when they don't — API routes are legitimately more granular than actions, not just a worse copy of them.

## Syllable Structures

Syllable structures reused the phoneme CRUD pattern almost entirely — Svc functions, route skeleton, list view — much of it harvested directly from the phoneme code. (This stretch happened during a Claude Code outage, so it was 100% hand-written; in hindsight, harvesting a working pattern from elsewhere in the same codebase isn't meaningfully different from reusing a known-good algorithm off Stack Overflow.) The form lets a user build syllable templates out of sequences of phonemes and/or phoneme groups, following the same add/edit-toggle pattern as the phoneme form.

Extracting the syllable template's TypeScript type via `z.infer<>` was the highlight of this stretch. The actual mechanism for getting a template through a form action was more debatable: the template state gets serialized to a JSON string in a hidden input and re-parsed inside the server action. It works, and stringify/parse isn't performance-relevant at this scale, but the packaging and unpackaging felt like a smell rather than a clean solution. The slot-adding portion of the form itself was handed to CC after running out of steam on frontend work for the day — a deliberate "convenience tax" tradeoff, justified specifically because it didn't need to touch the Svc layer or actions, only presentation.

That tradeoff surfaced a real bug shortly after: malformed JSON passed through the hidden input would throw inside the server action and bypass the `Result` contract entirely, rather than failing as a normal validation error. The fix reinforced a principle already established for actions generally — every value coming through an action is untrusted regardless of whether it "should" be internally generated, so `JSON.parse` needed to be treated as its own validation step, separate from the schema-level `safeParse` that was already correctly checking the parsed shape.

The API-route pass for syllable structures also caught pre-existing wrong HTTP status codes. By this point the visual state of the app was actively grating, but fixing it got deliberately deferred: rules — the last and most complex piece of planned CRUD/logic work — hadn't been built yet, and a real UI pass made more sense once every page's final shape and layout needs were actually known.

## Word Generation Engine

The wordgen Svc function is where the project's first genuinely complex logic lives: turning syllable templates into usable phoneme lists, using most of the DB-query techniques accumulated so far, including the first real use of `Promise.all` (two independent-but-both-required queries running in parallel). The core generation logic was ported from an old personal `wordgen.py` script wherever the translation made sense. This is also where RNG calls (`Math.random()`) ended up scattered throughout the file, which immediately made the logic harder to reason about and impossible to unit test.

This section was also the clearest jsonb tradeoff case in the project. Storing syllable templates as jsonb is easier to work with once you have the shape, but jsonb can't hold a real foreign key — so deleting a phoneme or group that's still referenced inside a template needed its own explicit check, which meant expanding `Result<T>` for the first time to represent a `conflict` outcome. A dedicated `slots` table was considered as the "more correct" alternative and rejected as its own kind of inefficiency. Individual numeric constraints on template slots also turned out to need individual validation messages rather than one blanket validation failure, since a single opaque error wasn't useful when the actual constraint violated could vary per field. And because generation can in principle run indefinitely against an unsatisfiable template, an escape hatch that returns a partial result was built in, with the decision of what to do with a partial result deliberately deferred to the caller rather than decided in the Svc layer. (Per-slot generation weights, instead of the current flat optional-slot setting, were considered and explicitly rejected as scope creep — "no conlanger is that obsessive," logged as a reminder of where the polish well goes bottomless.)

The scattered-RNG problem got addressed directly afterward: `wordgen.ts` was refactored so every previously-impure function takes an RNG implementation (Mulberry32) as an argument instead of calling `Math.random()` directly, confining all actual randomness — plus DB queries and seed generation — to the outer shell. This is a general functional-programming lesson worth carrying beyond this project: isolating randomness is what makes testing edge-case-heavy logic tractable at all. It's also the reason wordgen has real unit test coverage while most of the rest of the CRUD-heavy codebase doesn't (deliberately — this project doesn't have a strong sense yet of where integration tests would actually be worth the cost, but unit-testing the pure logic here was clearly both viable and necessary).

The wordgen route itself (pick templates — must have at least one — and a syllable-length range, defaulting to 1–1) raised architecture questions bigger than the feature itself: rules might eventually need to remember syllable bounds, lexemes might need multiple notations given phonemes carry an optional IPA field alongside a mandatory symbol, and the generation pipeline collapses everything down to plain words with no way to recover the generation context afterward. The resolution: words banked directly from the wordgen page can carry that context because they never leave the pipeline; words a user types in by hand are simply trusted as-is, with no rules or bounds applied retroactively — the pragmatic compromise between UX and schema rigor.

Finishing the form (short of the "Add to Dictionary" step) also settled a `useActionState` vs. `useTransition` question. `useActionState` had been the default tool so far despite feeling clunky (binding extra args via `Function.prototype.bind` reads as "cursed"), but this page is functionally not a form submission — it's stateful values being passed as Svc parameters through a server action — so `useTransition`'s non-blocking model fit both semantically and functionally, the first time in the project it was clearly the better tool for the job rather than the default.

## Phonotactics Validator

The phonotactics validator checks a word against every syllable template in a language and surfaces a warning — deliberately advisory, never a hard block on manually-entered words. There's no simple way to do this correctly: templates with optional slots mean the actual syllable-shape space is combinatorial, since each optional slot effectively produces a new template variant to check against. That makes the check inherently slow, and it needs to run infrequently and without blocking the UI as a direct consequence.

## Dictionary & Lexemes

Each dictionary entry (lexeme) got a row for term/notes/tags, with senses (part of speech + definition) as an uncapped subtable. A join query pulls a lexeme with all its associated details — by this point the pattern was getting genuinely easier to reach for, though "just fetch everything and merge it by hand" was still the instinct that had to be actively overridden, likely a holdover from how much manual merging wordgen required.

Importing generated words from the wordgen page into the dictionary raised a real design dilemma: should an imported word be required to have at least one sense? Enforcing that opened a window where a word could be inserted and its sense insertion could fail independently, leaving an inconsistent partial state. The resolution was to concede the constraint — allow blank words, and widen the sense schema to accept empty-string fields — which also means the current UI can add senses with no text filled in yet. The scale of frontend complexity this page was going to eventually need was already visible here; the actual UI pass was deliberately deferred again, same as syllable structures, until after rules.

Editing and deleting lexemes/senses surfaced an ownership-check pattern not seen elsewhere in the app: lexemes carry a `language_id`, but senses only carry a `lexeme_id`, so the standard "check the language belongs to the user" pattern doesn't reach senses directly — it needs two steps, first resolving the user's owned language IDs, then the lexeme IDs that belong to those. Functional, but acknowledged as architecturally uglier than it needed to be, and a candidate for restructuring the Svc-layer template later. Two smaller notes from this stretch: function arguments needed JSDoc because the Svc functions kept getting mixed up about what they actually expected, and a growing amount of ownership/validation boilerplate was clearly ripe for extraction — deliberately deferred rather than acted on immediately, flagged at the time as the "endless polish" voice and set aside until the dictionary route was actually finished.

The edit-mode UI (lexeme edit/delete, sense add/remove/update) didn't fit any existing form convention cleanly: the "add sense" affordance being permanently visible didn't match how other pages worked, but senses' need for independent management didn't fit the existing form patterns either. What shipped is an edit mode with per-item saves and no "cancel back to previous state" option — readable and functional, staying as close to existing conventions as the actual requirements allowed, including two separately-placed delete buttons (inline in the edit form, and in the row's actions column) that both felt legitimate rather than redundant.

## Svc Layer Refactor

By this point roughly 40 functions across the Svc layer were repeating the same ownership checks and input-parsing boilerplate. The fix split that duplication into two dedicated modules (ownership, parsing) and extracted `Result` constructors out from being imported bare. The change itself wasn't conceptually hard, just too large to hand-check function-by-function — Claude Code did the mechanical rewrite across the whole layer, and the verification step (rerunning the wordgen/phonotactics unit tests, confirming pages still worked) happened before committing. Auditing a change at that scale is still real work, but clearly less work than inserting ~40 near-identical edits by hand. Whether this constituted "endless polish" or legitimate scope was debated at the time and left unresolved — the working answer was that pre-defining the scope up front is what kept it from being polish, though that's flagged as a metric worth re-examining rather than fully trusted.

A parallel pass did the same thing for the API routes: roughly 16 routes were independently reimplementing the same `Result` → HTTP status/response mapping. Consolidating that into a shared helper caught real pre-existing bugs (wrong status codes on a few routes) as a side effect, and — like the Svc-layer extraction before it — makes that entire bug class structurally impossible going forward, since every route now goes through one shared mapping instead of reimplementing it.

## Search & Filtering

Dictionary search/filter (by term, senses, notes, or tags) and alphabetical/reverse-alphabetical sorting came down to one real decision: component state vs. URL params. State won — easier to implement, at the cost of not being shareable or bookmarkable. That tradeoff was judged acceptable specifically because shareability doesn't actually pay off under the current architecture: languages are locked to their owning user, so there's no one to share a search link _with_ yet. URL params remain the likely right answer once/if languages become shareable, but building for that before it exists would have been solving a problem the app doesn't have.

## Test Infrastructure

A dedicated Clerk test account got set up for feature verification, alongside registering Microsoft's official Playwright MCP server at the user level. Clerk makes throwaway test accounts trivial — appending `+clerk_test` to an email skips verification entirely, with the confirmation code always `424242` — which made automated sign-in straightforward. Digging into _why_ Postman kept behaving inconsistently during this same stretch explained the session-cookie mechanics properly: the 7-day session lives on Clerk's servers, but the `__session` cookie the app actually checks is a 60-second JWT that `clerk.js` refreshes every 50 seconds in-browser, invisibly. Postman doesn't do that refresh dance on its own, hence the intermittent failures — and confirming this also confirmed that a real API consumer (e.g. a mobile client using Clerk's SDK and its own `getToken()`) would never hit the same problem. The practical fix for Postman specifically was a longer-lived JWT template fetched via `window.Clerk.session.getToken({ template: 'postman' })`, rather than manually resyncing the snapshot.

The fuller end-to-end setup came later, after v1.0, once relying on Claude Code to derive Playwright tests from scratch for each feature (as happened during the [public demo language](#public-demo-language) work) proved slow and token-expensive in a way that a standing test suite wouldn't be. `@playwright/test` was added properly alongside the `verify` skill, but it deliberately isn't wired into CI: there's no dedicated test database, no CI secrets (adding them would be a real security-posture change, not a small one), exactly one shared Clerk test account, and — because none of this was planned for upfront — no `data-testid` attributes anywhere in the app yet. Given those constraints, e2e tests run manually before pushing rather than automatically on every push.

## Tags & the isUniqueViolation Bug

The tag system mostly mirrors the phoneme-groups relational setup — a language-scoped `tags` table plus a join table for lexeme attachments, reusing the same relational patterns already established there.

This is also where a real pre-existing bug got found and fixed: `isUniqueViolation` in `app/lib/ownership.ts` was checking for a `.code` property directly on the caught error object. But `drizzle-orm` (0.45.2) wraps driver errors in a `DrizzleQueryError`, with the actual Postgres error nested one level down in `.cause`. That meant every unique-violation catch in the codebase — including pre-existing ones in the phoneme-groups code — had never actually been matching, and were silently letting uncaught 500s through instead of returning a proper `conflict` result. A one-property fix, but one that had been silently broken since it was first written.

## Rules System

Rules — a phoneme or group targeted by a rule mutates into a different phoneme based on surrounding context — is the last planned piece of CRUD/logic work, and structurally the closest analogue is syllable structures: dependent on phonemes and groups, but with the actual references stored inside JSON, so verifying that a rule's targets still exist is an extra step rather than something the DB enforces directly. That verification got handled with a mix of helper functions and, for the more complex cases, raw SQL directly — a deliberate choice to reach for a "bigger tool" despite acknowledged unfamiliarity with SQL at that level, flagged afterward as worth revisiting to see whether the newer patterns elsewhere in the codebase would actually be a cleaner fit than the raw-SQL approach taken here. Reordering rules (an up/down "shift by one" control) needed its own specialized SQL to swap two rows' positions atomically.

Rules initially shipped disconnected from wordgen entirely — created and manageable, but with no effect on generated words yet. Playwright plus the dedicated test account (by now folded into the `verify` skill) meaningfully improved this stretch of work, since it meant both a personal manual pass against a real sample language _and_ an independent CC-driven pass against the same account were available before anything got called done.

Wiring rules into wordgen required reworking the wordgen pipeline first. The existing pipeline de-tokenized phonemes and groups into raw output before assembling syllables — but rules only carry tokens, and need to apply to a _completed_ word, not partially-assembled syllables. In hindsight this was a real design failure: data got collapsed into its final shape before anything actually needed it in that shape. The rework carries tokens further through the pipeline so the final output is unchanged from the user's perspective, but applying rules no longer needs an extra conversion step. Once wired up, `applyRules()` takes a `WordToken[]`, walks the rule list looking for matches, and applies changes in a single non-recursive pass — it does not re-check its own output against earlier rules before moving to the next position. Not necessarily a bad design decision on its own, but one that needs to be documented so the behavior is legible to a user rather than surprising.

## Overview & Timestamps

The language overview page got real content (stat cards), the landing page got an actual pitch instead of a placeholder, and Clerk's built-in sign-in/sign-up pages got replaced with custom routes (first real exposure to Next.js route groups — `(group)` — and optional catch-all segments — `[[...segment]]`). The bigger lesson here wasn't technical: the overview page wants to show "what changed recently," and nothing in the schema tracked _when_ anything happened, which is a direct consequence of not thinking about it upfront rather than a Next.js problem.

Timestamps got added to every table as a direct follow-up — a low-risk change (defaulting to current time, no Svc-layer impact) that unlocked recency sorting on the dictionary route and real content for the overview page's "recently added" section, plus test coverage for the relative-time formatting that recency display needed. The general lesson: creation/update timestamps are a near-zero-cost addition with outsized future payoff, and should be there from the start of a schema next time, not retrofitted. This was also a point to note that testing coverage had been improving organically — getting better at recognizing which new logic actually warranted a test as it was being written, rather than only in hindsight — flagged as worth a dedicated coverage-audit pass at some point rather than assumed to be complete.

## The Big UI Update

The big visual pass, deliberately deferred all the way until every page's final shape was known: a new color palette, shadcn/ui and its supporting pieces, and a set of reusable UI components applied across the whole app. It ended up substantially less painful than expected, largely because automated find/replace made a consistent codebase-wide rollout tractable — which is itself filed as another case of "should have been part of pre-planning," this time one that got lucky rather than one that caused a problem. Technically, this section also left a partial black box: `cva` (class-variance-authority) is clearly what's composing the variant style templates inside each component, and the pattern is legible enough to follow and extend, but not yet legible enough to say confidently that it could be written from scratch without a template to copy.

## v1.0 Shipping

The v1.0 checklist ran end-to-end through Claude Code, with review-and-confirm as the primary mode rather than hand-writing each step — a deliberate change given this was the first time actually publishing a project at this scale, and having both a personal checklist _and_ something that could execute against it while being guided and verified was more valuable than doing it solo. The concrete work: retiring `drizzle-kit push` in favor of committed migrations (generating a baseline migration off the current live schema, then hand-inserting its hash into `drizzle.__drizzle_migrations` since `drizzle-kit` has no real baseline command, with a Neon branch snapshot taken first as the actual rollback point); adding CI (lint/typecheck/test on every push and PR) plus a standalone `typecheck` script; fixing pre-existing type errors in test files that the new script exposed; README screenshots; `error.tsx`/`not-found.tsx` boundaries that had never existed; and finally renaming the project to conlang-studio, tagging, and pushing `v1.0.0`.

The single biggest technical lesson of the project surfaced here: **`next build`'s TypeScript pass only checks files reachable from routes and pages** — not the whole project — despite `tsconfig.json`'s `include` covering every `.ts`/`.tsx` file and `strict: true` being on. Two test files had real type errors (mock rows missing `created_at`/`updated_at`) that `next build` had been silently ignoring the entire time; only `tsc --noEmit` actually caught them, which is exactly why `typecheck` exists as its own script and its own CI step now, distinct from `build`. Secondary lessons: `drizzle-kit` has no built-in way to baseline an existing database against a fresh migration — it just needs a `hash` + `created_at` row in `drizzle.__drizzle_migrations` matching the migration file, nothing more — and Neon's actual point-in-time-recovery window on this plan is only 6 hours, which is why the manual branch snapshot, not PITR, was the real safety net for this migration.

## Retrospective

There's a lot that I learned here. It was my first big excursion into a project with a real backend and I think it went well. Beyond the actual tools I had to learn, there's the matter of architecture — the app structure and the DB schema were things I was always having to think about and work with. Two things came up repeatedly across this log: the endless polish trap and the failure to pre-plan. Endless polish is self-explanatory; the goal was v1.0.0 — a fully deployed, feature-complete application — and that goal isn't achievable if I keep going back and perfecting forever. I remember, back when I was first learning to code, thinking the ideal program was one that did just one thing and did that thing as well as possible. Back then it was console scripts; now it's a full-stack web app. The failure to pre-plan is a different thing. I can't in good faith say I should have seen it all coming — it was my first time working at this scale, and I came in with very little. What I can say is that every time that failure got noted is something to look back on next time and think through how it could have gone better. Is the app perfect? No. I'll likely come back to improve it later. Plenty of loose threads and deferred updates remain, but that's beyond v1.0.0. After 40 consecutive days of working on it, I think I'm good to let it sit for a second.

## Public Demo Language

A recruiter or a random visitor hitting Clerk's sign-in wall before seeing a single page of the app is a bad first impression, so this added a public, read-only demo language: an `is_public` column on `languages` (via a proper committed migration, the first schema change since migrations replaced `db:push`), a new `requireVisibleLanguage`/`parseAndRequireVisibleLanguage` pair in `app/lib/ownership.ts` alongside the existing owned-only helpers, six read Svc functions (plus `generateWordSvc`) widened to accept `user: DbUser | null`, all six language subpages reworked to resolve visibility instead of redirecting straight to sign-in, and a `canEdit` prop threaded through all seven client components so mutation controls simply don't render for a non-owner rather than being disabled. `proxy.ts`'s public matcher got widened accordingly. Around twenty files touched in total, verified with Playwright driving both a signed-in owner session and a signed-out incognito session against a language flipped to `is_public` directly through Neon.

The interesting part of this feature was a design decision, not a new tool. The first instinct was a `readOnly` flag on the resolved user object — simple, and sufficient for exactly one hardcoded demo account. The problem: it doesn't generalize. Real collaboration is a plausible future feature, and a flag on the _user_ can only ever express "this entire session is read-only" — far too coarse to express "this user can edit this language but not that one." `is_public` on the language row costs barely more today and is the right shape for that future: it becomes the "anyone" case sitting next to a future per-user grants table, instead of being something that has to be ripped out and rebuilt when that future arrives.

This work also settled the project's semver rules explicitly, since "what actually counts as a MINOR vs a PATCH" had been an open question since the previous entry:

- **PATCH** — copy/UI/bug fixes, no schema change, no new Svc functions.
- **MINOR** — additive new features/capabilities: new columns/tables, new Svc functions or routes, or widened existing behavior (like this entry's `DbUser | null` change) that doesn't change how existing callers work.
- **MAJOR** — anything that breaks existing data or existing usage: non-additive migrations (renames/drops, lossy backfills), or a fundamental rework of a core model.

## Error Handling Uniformity

A new shared error component and a shared `ActionState` type (moved into the client-safe UI directory) replaced the scattered inline error handling that had accumulated across the codebase — Claude Code did the sweep to find and replace prior instances, which also surfaced real gaps where a `Result`'s failure case wasn't being handled at all and errors were being silently discarded instead. The payoff is meant to land soon rather than immediately: the next planned pass is proper accessibility work, and the more UI surface already goes through shared, reusable pieces, the less rework that pass will require — another case, like timestamps and the UI update before it, of a thing that would have been cheaper to build in from the start than to retrofit later.

## Accessibility Pass

The previous entry called this out as next, and it landed as thirteen commits run end-to-end through CC with review-and-confirm as the primary mode, closer to the v1.0 checklist pass than to the earlier feature work, since by this point most UI surface already went through shared, reusable components, so most of this was a mechanical rollout of one established pattern rather than new architecture per page.

Target conformance settled on WCAG 2.0/2.1 A and AA — the level most real-world accessibility standards (ADA-adjacent legal requirements included) actually reference; AAA is widely considered impractical to hold an entire site to. That target ended up written down explicitly in `CLAUDE.md` only after the fact, caught by a `doc-sync` pass: `e2e/a11y.spec.ts`'s own comment referenced "CLAUDE.md's a11y notes" for the conformance level before any such notes actually existed there. Small, but a real instance of the discipline catching its own gap instead of shipping a comment that pointed at nothing.

The pass touched a lot of surface for something mechanical: a skip link plus one `<main>` landmark per route, heading-hierarchy fixes on pages that had drifted (phonemes, dictionary, wordgen), `aria-invalid`/`aria-describedby` wiring from every input to its `FormError` (which also picked up `role="alert"` so the message announces itself on mount, no separate `aria-live` region needed), and a `required` prop on the shared `Label` component — the visual asterisk it renders is `aria-hidden`, since the actual semantic cue for assistive tech is the input's own native `required` attribute, not the asterisk. Wiring that up over the dictionary's sense form also caught a small pre-existing doc bug: `createSenseSchema`'s JSDoc claimed `part_of_speech` was allowed to be empty, but the schema itself had already had `.min(1)` on it the whole time — the comment was simply wrong, and had been since before this pass started.

Two new focus-management hooks came out of this: `useFocusOnError`, which moves focus to the first invalid field on a failed submit, and `useReturnFocusOnExit`, which returns focus to the button that opened an inline edit once that edit closes, rather than letting focus silently drop to `<body>` when the editing control unmounts. `useFocusOnError` needed a real fix mid-pass: a field's error and its "no longer pending" disabled-state flip can land in two separate renders under a `useTransition`-driven commit, and the first version of the hook would sometimes try to focus a still-disabled input and silently no-op. The fix was to deliberately leave the hook's "already handled" flag unset when the field is still disabled at the moment the error first appears, so the effect retries once `disabled` actually flips false — a genuine bug caught during the work, not a hypothetical edge case guarded against on spec.

Verification split into static and dynamic halves. Statically, `eslint-plugin-jsx-a11y`'s full `recommended` rule set got layered on top of `eslint-config-next`'s baseline, which turned out to only wire up 6 of the plugin's rules on its own — nowhere near enough coverage to lean on alone. Dynamically, a new `e2e/a11y.spec.ts` runs `@axe-core/playwright` against both signed-out and authenticated pages on a dedicated `chromium-a11y` Playwright project. The first version of that spec under-scanned: the delete-confirmation dialog renders through a Radix portal, outside the normal DOM flow, so a scan taken only against the page's default state missed it completely. The fix was scanning explicitly while the dialog is open, not just before and after it. That, plus axe-core's own honest ceiling — automated scanning catches something like a third of real accessibility issues — is the actual takeaway from this stretch: the tooling complements a manual keyboard/label pass, it doesn't stand in for one.
